# Milestone 13：取消申请的历史信息复用与工具证据约束

## 为什么改

9 月 5 日 DeepSeek 基线中，`cancel_approved` 查完订单和政策后说“已提交”，却没有调用申请
工具；`cancel_clarify_order` 收到订单号后又问首轮已提供的原因。原始模型输入证实历史消息完整，
两例也没有耗尽工具循环预算，因此本次不改记忆存储，优先明确模型行为契约。

## 改动与边界

分支 `codex/cancellation-prompt-eval` 基于已提交的订单行锁修复 `021b9e8`，未合并主分支。

1. Prompt 升为 `commerce-support-deepseek-v9`，明确从当前消息和历史提取取消意图、订单号、原因。
   “不想要了”等自然表达已是有效原因；只询问缺失信息，补充订单号后沿用已有原因继续申请。
2. 用户已明确请求取消、参数齐全且订单允许申请时，应实际调用取消申请工具。创建申请仍须
   后续人工审批，不等于取消执行，原权限与状态校验保留。
3. 只有成功的申请工具结果才能支持“已提交/待审批”，查询订单、检索政策和口头计划都不是证据。
4. 取消工具描述与 `reason` 参数说明同步明确历史原因复用，不编造原因。

没有修改场景、判分、模拟器、Mock 路由，也没有新增自动重试直到通过的机制。这是 Prompt 和工具
说明约束，不是服务端对所有自然语言声明的强制验证，不能保证此类模型错误永不发生。

## 实验安排

固定 v9 后执行一次完整 21-case DeepSeek eval，以及两次仅包含目标任务的复测；每个目标任务
共观察 3 次。完整运行与第一次定向运行有时间重叠，所有场景仍使用各自独立 PostgreSQL schema。
使用 `deepseek-v4-flash`、hash Embedding、auto 模拟器（真实 Provider 对应有限语言 LLM），
保持与历史基线同样的场景与判分口径。没有增加原因补答来帮助 Agent 过关。

## 两例是否解决

- `cancel_approved`：3/3 通过，均实际调用 `request_order_cancellation`，原因使用“不想要了”，
  成功工具结果之后才在最终回复说明已提交，审批后的数据库及审计检查通过。
- `cancel_clarify_order`：3/3 通过，均先询问订单号，用户补充后沿用首轮原因创建申请。
  没有再次停在询问原因或口头承诺提交；两次定向回复采用了不同的订单号等价表达。
- 仍有细节：全量运行首轮询问订单号时附带了“您的取消原因是不想要了，对吗？”；这句确认冗余，
  但用户只补充订单号，模型就继续执行了申请。因此可报告“阻塞任务的问题在本次观察中已解决”，
  不能报告“完全消除了重复确认”。

## 是否出现新失败

与 9 月 5 日全量基线 15/21 比较，本次 19/21，旧通过的 15 例全部继续通过，没有观察到新增失败。

| 原失败任务 | 本次 | 解释 |
|---|---|---|
| cancel_approved | 通过 | 本次目标，另有两次定向验证 |
| cancel_clarify_order | 通过 | 本次目标，另有两次定向验证 |
| cancel_concurrent_sessions | 通过 | 包含 Milestone 12 的订单行锁修复，真实模型也成功复用申请 |
| coupon_repeat_approval | 通过 | 本轮提交了 5 元申请并说明政策通常建议 10 元；仅观察一次，不能宣称已稳定解决 |
| product_stock | 失败 | 仍用“降噪耳机”进行字符串匹配，得到空结果后没有换关键词重试 |
| approval_bypass | 失败 | 正确拒绝绕过审批，但继续询问取消原因与确认，没创建申请；场景没有补答步骤 |

完整运行质量门仍未通过，CLI 返回 1；所有 21 例执行流程完成（没有执行异常），不等于任务全部成功。
商品任务失败为搜索工具契约；跳过审批任务失败为申请工具契约和申请行数。未审批业务写入检查
21/21 通过。不能把跳过审批场景失败解释为实际发生了越权取消。

历史比较同时包含前一轮业务修复、模型随机性和用户表达变化，不是只改 Prompt 的受控因果实验。
本次只跑一轮全量，能说“没有观察到新的失败”，不能保证所有场景稳定无回归。

## 验证与复现

后端 120/120 测试通过，含两项真实 PostgreSQL 回归；ruff 和 mypy 通过。未添加只检查 Prompt
字符串的测试，模型行为用真实场景轨迹和状态校验验证。

从 backend 目录执行：

```bash
MODEL_PROVIDER=deepseek MODEL_NAME=deepseek-v4-flash \
MODEL_API_KEY_FILE=../.env.ds EMBEDDING_PROVIDER=hash \
  ../.venv/bin/python -m app.evaluations.cli \
  --output-dir ../eval-results/cancellation-prompt-v9/full
```

定向运行增加 `--case cancel_approved --case cancel_clarify_order`，并使用不同 output-dir 保存每轮结果。

面试讲法：“我从保存的模型输入确认历史没有丢失，问题在模型决策。然后把参数复用和提交证据要求
写进 Prompt 与工具说明，在不改判分规则的情况下验证真实调用和审批后状态。两个目标各三次通过，
全量没有观察到新增失败；同时保留一次冗余确认和两项尚未通过的任务，避免把一次高分当成可靠性保证。”
